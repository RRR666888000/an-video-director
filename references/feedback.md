# 使用反馈怎样变成改进

在用户反馈体验、要求修结果或继续优化Skill时读取，不让普通创作每次走反馈流程。

## 先定位问题

利用当时请求、实际回答/成片和差距，缺关键上下文只追问最影响定位的部分。把“没有网感”落到可观察问题，如词语陌生、开场解释太久、字幕遮挡、音乐与人物状态不符。

| 类型 | 处理 |
|---|---|
| 本次素材/账号信息不足、工具失败 | 补材料或修交付，不写成所有用户的门槛 |
| 个人风格、此项目选择 | 当前项目遵循；跨次保存依用户授权和宿主机制，不写成全局审美 |
| 可复现的判断/检索/路由缺陷 | 授权更新时对对应参考或工具作最小修复 |
| 观看/投放效果不及预期 | 对照目的与口径，不能用单次结果直接否定理论 |

只提出体验或质疑，先解释/修正本次结果，不将每次反馈视为发布、安装或持久化授权。要求更新Skill时完成修改、必要验证和交付，不重复索要已有授权。

## 改动有对照

记录足够复现的“原请求→问题→期望行为→最小修复→回测”。需要持续维护时在项目/工作目录保留轻量记录，不默认放入可分发核心，不记录无关私密信息。

用原场景确认修好，再检查相邻场景是否过度修正。例如“工作室日常被硬加卖货结尾”修复后，明确要求千川时仍应给具体进房动机。

判断问题用真实或明确虚构的场景检验目标、证据、可行性和边界，不只匹配措辞；检索/文件问题用确定性输入核对。一次模拟成功不等于传播效果已验证。

## 控制规则增长

优先更新已有方法和示例，不断追加“永远/必须”会让Skill变僵。共享同一原因的案例合并，策略与适用条件一起写，用户偏好保留为项目选择。

复盘可以改变下次建议，不代表模型被重新训练或无记录也能永久记住；跨次先读已有项目版本和记录。
